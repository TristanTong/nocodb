# 上游功能对比与选择性开发计划

| 项 | 内容 |
|----|------|
| 项目名称 | mlnocodb |
| 本地基线 | NocoDB `0.301.2`（分支名可能含 `0.301.3`） |
| 对比上游 | [nocodb/nocodb](https://github.com/nocodb/nocodb) 标签 **`2026.07.0`**（发布于 2026-07-14） |
| 文档版本 | v0.1.0 |
| 编写日期 | 2026-07-23 |
| 策略定位 | **保留自托管 Community 免费能力**；从上游 **选择性** 移植实用功能，避免整仓升级 |

---

## 1. 目标与原则

### 1.1 业务目标

1. 继续以当前版本为产品基线，保留已落地的免费/自托管能力与本地改造（Vastbase、PG Meta、6000 段端口、6100 生产 UI 等）。
2. 对照上游最新标签，识别「显眼且实用」的能力，**按优先级 cherry-pick / 对照重写**，逐步迭代本地 NocoDB。
3. 不被动依赖官方 Cloud / Enterprise 授权路径；付费专属大功能默认不整包合入。

### 1.2 工程原则

| 原则 | 说明 |
|------|------|
| 钉住 CE 基线 | 主线保持 `0.301.2 + 本地补丁`，不以 `2026.07.0` 整仓 merge 为目标 |
| 按功能切片 | 一次只引入一个（或一小簇）CE 功能，独立分支与验收 |
| 以官方 Availability 为准 | 每个上游 Release 均有 **CE / Free vs Paid / Enterprise** 表，Paid 项默认暂缓 |
| 保护本地补丁 | Vastbase FK、Windows/SDK、端口、Meta PG、冒烟与性能门禁必须回归 |
| 安全优先 | 上游安全修复（SSRF、鉴权、依赖）优先级高于「炫技」功能 |

## 2. 版本对照

| 项 | 当前 mlnocodb | 上游 `2026.07.0` |
|----|---------------|------------------|
| 版本标识 | `packages/*/package.json` → `0.301.2` | 日历化版本 `2026.07.0` |
| 发布主题 | — | Calendar Sync & Image Annotations |
| 差距性质 | 跨多个大版本（约 `0.301.x` → `2026.04`~`2026.07`） | 不宜直接整仓合并 |
| 许可 | Sustainable Use License（fair-code） | 同系列；自托管仍支持 Community |

### 2.1 必须保留的本地能力（升级/移植时回归）

- 海量/Vastbase 外键 introspect（`PgClient` 避免 `UNNEST … WITH ORDINALITY`）
- Meta 库 PostgreSQL（`mlnoco`），非默认 SQLite
- 本地端口约定：Backend `6080`、Frontend 生产 `6100`、HMR `6110`
- Frontend 生产构建托管与打开 ≤3s 门禁（`pnpm test:frontend-open` / `TC-PERF-01`）
- 文档与自动化冒烟（`scripts/compat/run_smoke_tests.py`）

## 3. 免费 / 收费判断（纠正与确认）

### 3.1 结论摘要

| 判断 | 对错 | 说明 |
|------|------|------|
| 「新版本很多亮点开始收费」 | **部分正确** | 自 2026.05 起，甘特、Sync、书签、Smart Text、日历同步等**新大功能**多为 Paid |
| 「最新版大多数功能都不能免费用了」 | **不正确** | 自托管 **Community** 仍保留核心电子表格能力，且官方说明自托管仍有无限用户/存储路线 |
| 「Cloud Free = 自托管免费」 | **不正确** | Cloud Free 有记录数/席位等用量限制；自托管 Community 是另一套模型 |
| 「应整仓升到 2026.07.0 才能用好功能」 | **不推荐** | 跨版本迁移、EE 门控、授权与 workspace 模型变化风险高；宜选择性移植 |

### 3.2 官方口径要点

- **自托管 fair-code / Community**：核心能力继续提供；内部自用通常不需商业授权。
- **Cloud / 付费自托管**：AI、高级表单、Extensions、部分高级视图与同步等为增值能力。
- **若把 NocoDB 本身作为对外托管/转售产品**：需单独评估 Sustainable Use License 与商业授权，与「内网自用 fork」场景不同。

## 5. 推荐开发策略

### 5.1 总体策略：「钉住 CE + 功能货架」

```text
本地基线 0.301.2 + 补丁
        │
        │  只读跟踪 upstream tags / develop
        ▼
按 Release Availability 筛选 CE 功能
        │
        ▼
feature 分支：cherry-pick 或对照重写
        │
        ▼
回归：Vastbase / Meta PG / 6080+6100 / 冒烟 / PERF≤3s
        │
        ▼
打本地 tag（如 v0.1.1）并更新本 backlog 状态
```

**明确不做（短期）：**

- 直接 `merge` / 大跨度 rebase 到 `2026.07.0`
- 为使用 Gantt/Sync/Smart Text 而绑定官方付费 license 作为产品前提
- 把 Cloud 用量限制误解为自托管限制而放弃自托管路线

### 5.2 工程节奏

1. 添加只读 remote：`git remote add upstream https://github.com/nocodb/nocodb.git`（若尚未添加）。
2. 每个候选功能建分支：`feature/ce-<短名>`。
3. 优先官方 CE 提交的最小依赖集；无法干净 cherry-pick 时，对照 UI/API **在 0.301.2 上重写**。
4. 合并前必跑：
   - `python scripts/compat/run_smoke_tests.py`（含海量库与 `TC-PERF-01`）
   - `pnpm test:frontend-open`（6100 打开 ≤3000ms）
5. 文档：在本文件「Backlog」表更新状态；重大能力补充到 `01`/`04`/`06`。

### 5.3 与业务匹配

- 当前强项：**外部 PostgreSQL / Vastbase + 自托管免费核心能力**。
- 优先：**网格体验、导入、安全、公式、外部库稳定性**。
- 弱化：**App Sync / Docs 商业套件 / Oracle 插件**（除非出现明确业务需求）。
- 若 Paid 功能刚需：对照 UX **自研最小集**，挂在 CE 基线上，比整版升级更可控。

## 6. 迭代路线图

| 周期 | 主题 | 候选能力 | 主要验收 |
|------|------|----------|----------|
| **A** | 安全与外部库稳定 | SSRF/鉴权相关修复；schema sync / Link / 导出链路修复 | 海量库 + PG Meta 冒烟全绿 |
| **B** | 网格体验 | 展开记录侧栏；选区汇总；排序开关；复制行；批量列 | 日常录数/编辑体感；无回归 |
| **C** | 导入与表单 | Excel 跳过 sheet；导入建字段；表单草稿 | 业务导入与公开表单场景 |
| **D** | 公式与日历增强 | 校验和公式；`.ics`；多周/自定义日历 | 有对应视图与字段场景 |
| **E（可选）** | 自研类付费能力 | 轻量甘特 / 只读日历同步 / LTAR 显示列 | 明确不依赖官方 license |

建议单周期只交付 **1 个 P0 主功能 + 必要修复**，避免范围膨胀。

## 8. 验收与质量门禁

每个上游移植或自研能力合并前，至少满足：

| 门禁 | 命令 / 用例 | 标准 |
|------|-------------|------|
| 冒烟 | `python scripts/compat/run_smoke_tests.py` | 无新增 fail；海量相关用例通过 |
| 前端打开 | `pnpm test:frontend-open` / `TC-PERF-01` | `openMs ≤ 3000` |
| 双入口 | Backend `6080`、Frontend `6100` | 健康检查与登录页可用 |
| 本地补丁 | Vastbase FK、Meta PG | 无回归 |
| 文档 | 本 Backlog 状态更新 | ID 与周期对应 |

可选：为单项功能在 `docs/06-测试用例文档.md` 增加 `TC-UP-xx` 用例。

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 跨大版本 API / Meta 迁移不兼容 | 数据损坏或无法启动 | 禁止整仓 merge；功能级移植 + 备份 Meta |
| 误合入 EE 门控代码 | 功能看似存在但运行被挡或依赖 license | 合入前核对 Availability 与 `isEE` / 计划门控 |
| cherry-pick 冲突过多 | 工期失控 | 改为对照重写；缩小范围 |
| 破坏 Vastbase 兼容 | 数据源不可用 | 每个周期跑 `TC-COMPAT-*` / `TC-VB-*` |
| 6100 又改回 Vite 开发态 | 打开变慢 | 保持生产托管；HMR 仅用 6110 |

## 10. 下一步行动（可立即执行）

1. 确认 `upstream` remote，只读 fetch `2026.07.0` 与近期 tags。  
2. 从 Backlog 选取 **UP-A01（安全）** 与 **UP-B01（展开记录侧栏）** 做第一轮评估（依赖文件清单、能否 cherry-pick）。  
3. 评估通过后开 `feature/ce-expanded-record-side-panel`（或先做安全合集），按第 5、8 节落地。  
4. 每个周期结束更新本文件状态，并视需要同步 `docs/README.md` 版本说明。
